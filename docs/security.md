# Security notes

- **Bridge certificate validation.** Every CLIP API call is verified against Signify's two published Hue root CAs, and the certificate's common name is checked against the bridge id (Hue bridge certificates carry the bridge id rather than an IP, so the bridge id stands in for the hostname check). The check runs *before* pairing, so the DTLS client key, which the bridge mints once and shows once, is fetched over that checked connection. Early bridges that still carry a self-signed certificate fall back to trust-on-first-use pinning, and updating the bridge from the Hue app gives them the stronger check. On the manual IP step, setup may use Hue's discovery service to pre-fill the bridge address.
- **DTLS mutual authentication.** The entertainment stream's handshake enforces the server's `Finished` message, so the integration streams colours only to a device that proves it knows the pre-shared key.
- **ffmpeg protocol whitelist.** Every ffmpeg invocation is restricted to `http`, `https`, `tcp` and `tls`, so a stream or artwork URL is limited to network protocols and local ones such as `file://` are out of reach. Stream and artwork URLs come from your players, so ffmpeg may fetch them from wherever they point, including outside your LAN.
- **Log redaction.** Stream and artwork URLs are logged with their query strings masked (Subsonic auth tokens ride in query strings), so debug logs are safe to paste into bug reports.
- **Credentials.** The Hue app key, DTLS client key and optional Subsonic login are stored in Home Assistant's config entry storage, like other Home Assistant integrations. Home Assistant stores that data as plain text at rest, so keep your backups and config folder private.
